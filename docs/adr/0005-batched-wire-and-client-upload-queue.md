# The wire protocol carries batches, and the client queues uploads into them

A CI build puts thousands of objects, most of them a few KiB. Uploading each one as its own HTTP request, at most 4 at a time, made request overhead rather than bandwidth the limit on upload time. Every request now carries a batch of objects, and the client collects puts into batches before uploading them.

**Wire.** The single-object routes are gone; there is no compatibility path, as 0.x makes no stability promise. `PUT /cache/batch` takes a `multipart/mixed` body with one part per object and answers with a JSON array of per-object results in request order: `stored`, `skipped` (with the refused kind), `corrupt`, `rejected` or `error`. `POST /cache/batch-get` takes a JSON array of action IDs and answers `multipart/mixed`: a JSON manifest of the hits, then one content part per hit. A request that fails as a whole is `400` (malformed), `413` (over the limits) or `401`. The `415` status and `Gocached-Rejected-Kind` header of ADR 0004 are replaced by the per-object `skipped` result; the client's handling of a refused kind is unchanged. We chose multipart because `mime/multipart` streams in both directions, so no side holds a batch in memory, and parts carry headers for metadata. A JSON manifest followed by concatenated bodies would need a hand-written framing, and a custom binary format the same.

**Sizes and limits.** Each part declares its size in `Gocached-Size`, and the server bounds what it reads by those declared sizes, not by `Content-Length`. Bodies are streamed with unknown total length. This keeps a later `Content-Encoding` on the whole body possible without protocol changes: compression applies to the multipart stream as a whole, which is where small objects share redundancy, and limits apply to decoded bytes. Compression itself is not implemented. `GOCACHED_UPLOAD_BATCH_ITEMS` and `GOCACHED_UPLOAD_BATCH_BYTES` are read by both commands with the same defaults (256 objects, 4 MiB): the client's batching limits and the server's hard limits. A batch of one object may exceed the byte limit, so large objects still upload. A batch-get is capped at 1024 IDs; there is no download queue yet, so the client asks for one ID at a time.

**Interfaces.** `backend.Backend` and `chain.Chain` take and return batches. Put items open their content lazily, one at a time, so a batch of hundreds of local files holds one file descriptor. The bodies of one Get may share a single response stream and must be read in order. The `GOCACHEPROG` handler stays per object, because go sends one request at a time.

**Upload queue.** `internal/bundler` is a small generic batcher on `golang.org/x/sync/semaphore`: a batch is sent at N objects, B bytes or a delay T after its first object; an object of at least the small-object threshold goes alone; buffered bytes are bounded so a slow server applies backpressure to go's puts; handlers are bounded by a concurrency limit; Close flushes and waits up to the drain timeout, then cancels. We looked for a library first (`docs/research/upload-batching.md`): `google.golang.org/api/support/bundler` fits closest but is marked experimental and brings a heavy module, and the generic batchers we found count items rather than bytes or need a newer Go.
