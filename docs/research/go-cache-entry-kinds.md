# Go build cache entry kinds, their keys, and cross-machine reuse

Researched 2026-11-14 against the Go source at tag `go1.25.7`, the toolchain of the CI build that motivated this note. All links are pinned to that tag; `B` below stands for `https://github.com/golang/go/blob/go1.25.7/src`. Differences in go1.25.12, go1.26.0 and go1.27.0 are listed at the end. Items marked **(unverified)** could not be confirmed from source.

The question: which entries does `cmd/go` write to its cache, what goes into each key, which of them can hit on another CI machine, and which can gocached recognize from the bytes it sees?

## What gocached can see

With `GOCACHEPROG` set, `cache.Default()` returns the program cache instead of the disk cache ([default.go L36-L61][default]). A `put` carries an action ID, an output ID, a size and the body; a `get` carries only the action ID ([cacheprog.go L65-L91][request]). Action IDs are opaque SHA-256 sums. The kind of an entry can therefore only be read from a `put` body, never from a `get`.

Every key is salted with the Go version ([hash.go L46][salt]), so no entry hits across toolchain versions. Many entries are subkeys: `cache.Subkey(parent, desc)` hashes `"subkey:"`, the parent ID and a description ([hash.go L59-L75][subkey]). A subkey depends on exactly the parent's inputs and is only read after the parent hits.

## Entry kinds

| Kind | Written by | Key inputs | Leading bytes | Reuse across CI machines (same toolchain) |
|---|---|---|---|---|
| Package index | `openIndexPackage` | absolute module root and package dir; name, mtime and size of every immediate regular file | `go index v2\n` | Only with the same absolute paths, identical mtimes and the same time zone |
| Module index | `openIndexModule` | absolute module root in GOMODCACHE | `go index v2\n` | Only with the same GOMODCACHE path; unused with `-mod=vendor` |
| Compiled package | `updateBuildID` | file names and contents, dependency content IDs, tool IDs, flags, GOOS/GOARCH, module Go version; `dir <abs>` without `-trimpath`; cgo compiler and flags | `!<arch>\n` | Yes with `-trimpath`; without it only at the same checkout path |
| Compile and link stdout | `updateBuildID` | subkey of the compiled package | none; usually empty | As its parent |
| `srcfiles` list and objdir files (cgo output, cover output, cover metadata) | `cacheSrcFiles`, `cacheObjdirFile` | subkeys of the compiled package | none fixed; cover metadata may be empty | As its parent |
| vet facts | `vet` | vet tool ID and flags, the package's build action ID, dependency facts | gob stream, or empty | As the compiled package |
| C compiler identity and flag probes | `gccCompilerID`, `gccSupportsFlag` | absolute compiler path | path and stat text; `true`/`false` | Same image: yes. Separately installed compilers: the stored stat differs, so each machine recomputes and puts again |
| PGO profile | `pgoActor.Act` | `preprofile` tool ID and profile content | `GO PREPROFILE V1\n` | Yes |
| testmain source (`go list -test` only) | `list` | the generated content | `\n// Code generated by 'go test'.` | Yes |
| Test log | `saveOutput` | test binary link ID or content ID, cacheable `-test.*` flags, exec command | `# test log\n` | Yes when the test binary matches |
| Test output | `saveOutput` | subkey of the test log key and the hashed inputs the test touched | none; ends with an `ok` line | Only for tests that touch no files under the module root (see below) |
| Cover profile | `saveOutput` | subkey of the test output key | `mode: ` | As test output |

Sources by row: index [read.go L50-L119][index-keys], [L184-L245][index-io], [write.go L14-L20][index-write]; compiled package [exec.go L241-L419][build-action], [buildid.go L716-L734][archive-put]; stdout [buildid.go L651-L668][stdout]; srcfiles and objdir files [exec.go L1009-L1064][objdir]; vet [exec.go L1226-L1349][vet]; C compiler [exec.go L2362-L2579][gcc]; PGO [action.go L477-L537][pgo], header [serialize.go L30][pgo-header]; testmain [list.go L670-L681][testmain], [load/test.go L782][testmain-header]; test entries [test.go L2068-L2128][save-output], test log header [deps.go L121][testlog-magic], cover profile header [cover.go L39][cover-header].

Not every result is cached. Plain `go build` link outputs are never stored; only their stdout is. Executables for `go run` and `go tool` are cached only when the backend is the disk cache, so under `GOCACHEPROG` they are not cached at all ([buildid.go L736-L753][exe]).

### Recognizable bodies

Four kinds can be recognized by an exact prefix: index (`go index v2\n`), compiled package (`!<arch>\n`), test log (`# test log\n`) and PGO profile. The package and module index share the same encoding, so their bytes cannot tell them apart ([write.go L18-L44][index-write-enc]). Empty bodies are common: compile and link stdout are almost always empty, and empty vet facts and empty cover metadata also occur. An empty body cannot be attributed to one kind. Everything else has no fixed header.

## Package index keys

For packages outside the module cache (the main module, vendored packages and GOROOT), `dirHash` writes the Go version, the index version, the absolute module root and the absolute package directory, then for each immediate regular file its name, `ModTime()` formatted with `%v`, and size ([read.go L78-L119][index-keys]). `%v` uses `Time.String`, which includes the zone name, so the same instant renders differently under different `TZ` ([format.go L546][time-string]). Subdirectories are skipped. A non-regular entry, or a regular file modified less than two seconds ago, makes the package unindexed for that run: there is no get and no put.

Modules under GOMODCACHE use one whole-module index keyed on the Go version, the index version and the absolute module root, with no per-file data ([read.go L50-L76][index-keys]). This path is not taken for GOROOT, for modules outside GOMODCACHE, or with `-mod=vendor` ([read.go L158-L177][get-module]).

`-trimpath` is not consulted in either key. The payload also embeds absolute filenames: files are parsed under `filepath.Join(dir, name)` ([build.go L436][file-info]) and token positions are encoded with their filename ([write.go L105-L110][position]). Rewriting paths in the key alone would not make a payload relocatable, and gocached cannot rewrite the key anyway, because it only receives the hash.

`GODEBUG=goindex=0` turns both indexes off and Go reads the source directories directly ([read.go L37][index-enabled], [load/pkg.go L933-L940][loader]). The setting is undocumented: the `#` in `godebug.New("#goindex")` marks it as such and is not part of the key ([godebug.go L85-L107][godebug]).

Two consequences for CI:

- A fresh checkout gives source files new mtimes, so package indexes for the checkout never hit on another machine or in another workspace. GOROOT package indexes can hit when every machine has the same toolchain install at the same path with the same file times.
- Giving every file a constant mtime does not fix this safely. A same-path, same-name, same-size, same-mtime file with different content produces the same key and reuses a stale index. Go issue #69179 reports exactly this from a CI that set all mtimes to 1970-01-01 ([comment][issue-constant]), and a maintainer explains why identical size and mtime reuse the old index ([comment][issue-mtime]).

## Compile and link keys

`buildActionID` hashes each input file's name and SHA-256 content, not its mtime ([exec.go L390-L407][build-inputs]). Inputs include Go, cgo, C, C++, Fortran, Objective-C, header, assembly, syso, SWIG and embedded files. Without `-trimpath` the key also contains `dir <absolute package dir>` for packages outside GOROOT ([exec.go L254-L280][build-action]). The link key adds `GOROOT=<path>` unless `-trimpath` is set ([exec.go L1414-L1421][link-config]). So with `-trimpath` and the same toolchain, compiled packages are reusable across checkout paths and fresh mtimes.

## Test result keys

Results are cached only in package-list mode (`go test .`, `go test ./...`), only for packages inside a module, GOPATH or GOROOT, and only when every test flag is cacheable ([test.go L1748-L1806][eligibility]). The cacheable flags are `-benchtime`, `-cpu`, `-list`, `-parallel`, `-run`, `-short`, `-skip`, `-timeout`, `-failfast`, `-v` and `-fullpath`. `-coverprofile` and `-outputdir` are allowed but left out of the key. Any other flag, including `-count=1`, disables result caching but not the build cache.

The lookup has two levels ([test.go L1834-L1894][lookup]):

1. The test ID hashes the test binary identity, the cacheable flags and the exec command. It first uses the link action ID, so a hit avoids linking. On a miss Go links and retries with the binary's content ID ([test.go L1518-L1536][retry]). The test ID maps to the test log of the previous successful run.
2. The test log lists `getenv`, `open`, `stat` and `chdir` calls made through package `os` ([deps.go L70-L132][testlog], [os/stat.go L11-L27][os-stat], [os/file.go L410-L419][os-open]). `computeTestInputsID` hashes the current value of each logged input ([test.go L1933-L1991][inputs]). The test ID and that hash together key the test output.

For files, only stat data is hashed: size, mode, mtime and `IsDir`, together with the absolute path ([test.go L2009-L2065][hash-open]). Opening a regular file hashes its stat, not its content, and a file modified less than two seconds ago (or in the future) makes the result uncacheable for that run. `open` and `stat` of paths outside the package's root (its module root, GOPATH or GOROOT) are skipped; `chdir` is always hashed. `GODEBUG` is always included.

So a test that reads files under the module root misses on a fresh checkout or at another path, even when its binary, log and code all match. A test that touches no such files can hit across machines. Test output entries cannot be told apart by kind, because the same kind of entry is reusable for one test and not for another.

Results are saved only after a successful run, and both test IDs get a copy of the log and output ([test.go L2077-L2128][save-output]). `go clean -testcache` writes `testexpire.txt` into the local GOCACHE instead of deleting entries, and results older than that time are ignored ([test.go L840-L849][expire]). Under `GOCACHEPROG` the entry time is the one the program returns, or now when it returns none ([prog.go L259-L296][prog-get]).

## Local observations

These ran on go1.25.12, Windows/amd64, with `GOCACHEPROG` unset, so they confirm the source reading but say nothing about Linux or the remote server.

- Test cache, with one module containing a pure test and a test calling `os.ReadFile("testdata/input.txt")`, using `go test -x ./...` and `GODEBUG=gocachetest=1`:
  - Touching every `.go` file: both results `(cached)`, no compile or link.
  - Touching only the data file: the pure test stayed cached; the file test ran again with zero compiles and one link, the same test ID and a new input ID.
  - Setting the data file's mtime in the future: the file test ran with `file used as input is too new`.
- Package index:
  - Changing `import _ "fmt"` to `import _ "log"` (same byte length) and restoring the old mtime made `go list` report the stale import `fmt`, with the same index ID.
  - With `GODEBUG=goindex=0` it reported `log`.
  - Copying the unchanged files with their mtimes to another directory produced a different index ID.

## A CI build log

A user-supplied log (not in the repo) of `go build -trimpath -x` with `GODEBUG=gocachehash=1` on go1.25.7, Linux/amd64, vendor mode, through `gocached prog` against a warm remote, ended with:

```text
gocached: get=8707 hit_local=0 hit_remote=6048 miss=2659 put=2659 upload_ok=2659 upload_fail=0 drain=0ms
```

The log held 2,900 completed package index hashes, 2,899 compiled package hashes, 2,899 `stdout` subkeys and 9 `link-stdout` subkeys, with no compile, assembly or cgo commands and 9 link commands. The gets add up exactly: 2,900 index + 2,899 package + 2,899 stdout + 9 link = 8,707. So every compiled package and its stdout hit, 250 index entries hit (directories whose mtimes come from the toolchain install), and the misses were 2,650 indexes and 9 links. The puts were the 2,650 rebuilt indexes and 9 `link-stdout` entries. This is reconstructed from counts and source, not from a per-request trace. Uploading those 2,650 indexes bought nothing, because the next checkout gives them new keys again.

## Version differences

- go1.25.12 and go1.27.0 add a coverage-metadata hash to the cover profile key under `-coverpkg`, and store an empty sentinel when no profile was requested. go1.25.7 and go1.26.0 have neither.
- go1.26.0 and later also cache vet's stdout and a `fix.zip` subkey ([go1.26.0 exec.go L1382-L1383][vet-126]).
- Index hashing and `indexVersion` are the same in go1.25.7, go1.25.12, go1.26.0 and go1.27.0.
